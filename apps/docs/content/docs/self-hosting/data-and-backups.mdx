MausBot keeps its application state in its data folder, including configuration, transcripts, message attachments, device pairing state, and the SQLite message store. Where that folder is:

- The desktop app and an npm install: `~/.openmausbot` (`OMB_DATA_DIR` names another). In the desktop app, workspaces you add are in `~/.openmausbot-profiles/` (`<that folder>-profiles` with `OMB_DATA_DIR`); once this computer's bots have moved to My Cloud, This Mac's (or This PC's) is there too, as `default`, and `~/.openmausbot` keeps the copy from before the move.
- The Docker image: `/data/.openmausbot` inside the container, on its `data` volume (named `deploy_data` with path B's `deploy/docker-compose.yml`, `openmausbot_data` with the repository's root `compose.yaml`).
- A server set up with the installer: `/opt/openmausbot/data/.openmausbot` on the server, a folder rather than a volume.

## Move from the desktop app

To bring your computer's bots and chats to a server you run, use the desktop
app: connect the server with **＋ → Connect to a server**, then choose
**Make … my home** (with the server's name) in that server's menu on the rail,
or under **Settings → Phone & devices → Always-on home → Add a Mac mini or other
always-on computer** (on this computer's own page). It moves this computer's
bots, chats, memory and routines to the server, and this computer then works
for it. Bots' Data tables do not move.

The move is one-way: this computer's own server stops for good, there is no
button to move back, and the copy here is kept, frozen. It is offered only for
a server where nobody but you signs in, where this app is signed in as its
owner, and that runs a version new enough to take the move; and not while, or
after, this computer's bots move to My Cloud.

To copy instead of moving, or for a server with no desktop app nearby, use
export and import below.

## Export and import in Settings

Open **Settings → Import & export → Export full backup**. Choose a password of at least
12 characters and save the encrypted `.ombbackup` file. Keep the password
separately: there is no password recovery.

The backup contains this server workspace's bots, threads and complete message
records, attachments, custom avatars, instructions, memory, skills and supporting
files, routines and run logs, and non-secret settings. Drafts and preferences
from the browser performing the export are included too. It does not collect
another browser's unsent drafts.

**Saved account credentials and connections are not included.** Reconnect your
accounts on a new machine. Restoring does not overwrite credentials or connections
already present on the destination.

Encryption still matters: conversations, drafts, instructions and user files
are private and may contain secrets you pasted into them. These contents are
not automatically redacted, so do not treat the archive as safe to share.

If you have explicitly put a provider's login home inside ordinary workspace
files, move it into the excluded `providers/` directory or outside the workspace
before exporting or restoring. The app refuses that layout rather than copying
or replacing its credentials.

Wait for bots, approvals, provider sign-ins, and computer actions to finish.
Stop external editors and managed desktops that write workspace files. The app
temporarily pauses its own writers and takes a consistent SQLite snapshot. The
current limit is **10 GB of workspace files and 100,000 entries**; exceeding it
fails explicitly, never silently produces a partial backup.

Remote proxies and tunnels may impose smaller upload or timeout limits. For a
large import, use a direct connection to the server or its local desktop UI,
or configure your own reverse proxy's limits appropriately.

To restore, choose **Import backup**, select the file, and enter its password.
Validation shows its date, version, contents and exclusions before anything is
replaced. Type **REPLACE** to confirm, then fully quit and reopen the desktop app,
or restart the hosted server process. Closing a desktop window is not enough.

Restore **replaces**, rather than combines, workspace data. The previous data is
kept under `.openmausbot/.backups/safety-<restore-id>/`. A failed or interrupted
replacement recovers the previous files before the server loads them. Keep that
safety directory until you have checked the restored workspace. It contains
private data; do not share it.

The downloaded file is encrypted. Import validation and recovery also create
private, unencrypted staging and safety files under `.backups`. They contain
private workspace data and may contain secrets already present in conversations
or files. Protect the server's disk and account accordingly; these recovery files
are not protected by the export password. Allow extra free disk space for staging
and the previous workspace.

Only restore backups you trust: instructions, skills and bot permissions are
included. Scheduled routines and webhooks are paused, calendar
calls are not automatically restarted, and unfinished delegated work is not
replayed. Review and re-enable automation deliberately after restoring.

The old partial export is no longer offered in the sidebar. Existing
`.mausbackup.json` files can still be imported through **Teams** as independent
copies. Shareable team templates remain separate from full backups.

## What stays outside a workspace backup

- External project directories and default CLI login homes such as `.claude`
  and `.codex`. Reinstall providers and sign in again if needed on another host.
- Saved account credentials, API keys, connection settings, operating-system
  keychains, browser login/session homes, and phone pairing keys. Sign in or
  reconnect on the new machine; destination credentials remain untouched.
- VM/container disk layers and remote Boat/VPS files. Durable mounted files
  inside the workspace data directory are included, but the VM itself is not.
- Bots' Data tables (`bots/<id>/data.duckdb` and its working files in the data
  folder). A filesystem-level backup taken with the server stopped includes them.
- Other fleet workspaces, downloaded tools, caches, running processes, and
  active device sessions. Existing destination pairing and server identity stay
  in place; moving to a new server requires pairing with that server.

App-owned paths inside the data directory are adjusted on import. External
paths are not copied or rewritten; check them when moving between computers.

## Filesystem-level backups

Close MausBot before taking a filesystem-level backup so SQLite and configuration files are captured consistently. Preserve the entire `.openmausbot` directory rather than selecting individual database files.

Raw filesystem snapshots differ from Settings exports: they may include saved
credentials, CLI homes and browser sessions. A Docker snapshot of the whole
`/data` volume includes the container's CLI homes. Protect these snapshots as
sensitive data. For migration without saved credentials, use the Settings export
and reconnect accounts on the new machine instead.

Restore with the server stopped, preserving the original paths and ownership, then start it again. The [VPS backup instructions](/docs/self-hosting/deploy-vps#back-up) show the app-data archive and stop/start commands.

## The settings file and its dated copies

Every save of `~/.openmausbot/config.json` keeps a copy of the file as it was,
named `config.json.bak.YYYYMMDD-HHMMSS`, beside it; the last ten are kept. A
save never replaces a settings file it could not read or understand: it fails
and says so, so a file that cannot be read is never overwritten by a partial
one. A save that cannot keep its dated copy fails as well, so the settings file
is never replaced without a copy of it to go back to.

To go back to an earlier copy, stop the server and run:

```
openmausbot config backups
openmausbot config restore latest
```

The file a restore replaces is kept as a dated copy too, so the restore can be
undone. A restore only puts back a copy that is a settings file the server can
read, and never over a file it could not read or keep: nothing is lost to put a
copy back. These copies hold the saved keys and connections of the settings
file: they stay on that computer and are not part of a workspace backup.

## Do not copy secrets casually

Packaged desktop builds protect credentials using operating-system secure storage.
Copying the JSON directory alone does not necessarily make those credentials
usable elsewhere. Settings exports deliberately leave saved credentials and
connections behind; sign in again on a new machine. Raw filesystem snapshots
and automatic restore safety copies must be protected separately.

## Disposable computer filesystems

Local VM workspaces are mounted durably, but a self-hosted VPS container filesystem is intentionally disposable. Move important artifacts to a durable workspace, repository, or connected app before removing or upgrading a container.
