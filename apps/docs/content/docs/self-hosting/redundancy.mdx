A MausBot server keeps everything in one data folder, and only one server may run on it at a time. Redundancy is therefore one **active** server and one **standby** in another place: the standby keeps a copy of the active server's data, and starts on that copy only when the active server is gone. Never run both.

MausBot has no built-in standby or automatic takeover. This page is a recipe you run yourself, with plain tools (`sqlite3`, `rsync`, `ssh`, `cron`). Below, A is the active server and B the standby.

<Callout type="info" title="What you lose, and how long it takes">
  - **Lost:** everything since the last copy. With a copy every minute, about the last minute or two of chats, bot changes and files.
  - **Interrupted:** turns that were running on A stop with it. On B, ask again where a bot did not finish.
  - **Takeover time:** how long you wait before deciding A is gone, plus starting B, plus your address moving to B. In our test the server answered within a second of starting; the wait and the address change are yours to set, so plan on a few minutes.
</Callout>

## What makes up a server's state

Everything is under the server's home: its own folder (`.openmausbot`) and the engines' sign-ins beside it (`.claude`, `.codex` and others).

| Install | Folder to copy (`DATA`) | The server's own folder inside it (`STATE`) |
|---|---|---|
| [Installer](/docs/self-hosting/deploy-vps#quick-start-one-command-on-your-own-domain) | `/opt/openmausbot/data` | `.openmausbot` |
| npm service, user `maus` | `/home/maus` | `.openmausbot` |

Most of it is ordinary files. Four are SQLite databases the server keeps open and writes all the time: `messages.db`, `runtime.db`, `bursts.db` and, when present, `sync/index.db`. The first three run in WAL mode: the newest changes sit in `messages.db-wal` (and the others' `-wal` files) until SQLite folds them in. **Do not copy these files with `rsync` or `cp` while the server runs.** In our test, a plain copy of `messages.db` taken while the server ran was missing every message still in the WAL file. SQLite's own `VACUUM INTO` makes a complete, consistent copy while the server keeps writing.

The folder also holds a **lease**, `.openmausbot/openmausbot-server.lease`. It names the process and machine running the server. A second server on the same folder refuses to start, and so does a server on a copy of the folder whose lease names another machine, until you remove the lease. The recipe keeps the lease in the copy on purpose: a standby started by mistake stops there.

The lease does **not** stop A from starting again on its own folder while B runs. We tried it: A came back on its own data, beside B, with the same server id and different chats. Keeping A stopped is your job (step 1 of the takeover).

## Set up the standby

You need `sqlite3` (3.27 or newer) and `rsync` on both servers: `sudo apt-get install -y sqlite3 rsync` on Ubuntu.

1. **Let B reach A over SSH as root**, with a key used only for this. B pulls from A; A gets no way to write to B.
2. **Install MausBot on B the same way as on A, at the same version, and leave it stopped.**
   - Installer: run the install command with the DNS check off, since your domain still points at A. It ends saying HTTPS did not answer: B cannot get a certificate yet, and everything else is installed. Then take A's `.env` (it names A's version), download that version and stop B:

     ```sh
     curl -fsSL https://raw.githubusercontent.com/milind-soni/OpenMausBot/main/deploy/install.sh | sudo OMB_INSTALL_SKIP_DNS=1 sh -s -- --domain maus.example.com
     sudo scp root@server-a.example.com:/opt/openmausbot/.env /opt/openmausbot/.env
     cd /opt/openmausbot && sudo docker compose pull && sudo docker compose stop
     ```

   - npm service: install the same `openmausbot@X.Y.Z` and the same systemd unit as on A, then `sudo systemctl disable --now openmausbot`.

   After every update of A, bring B to the same version (take `.env` again and `sudo docker compose pull`), and keep it stopped. B must never be older than the data it copies.
3. **On A, save this as `/usr/local/bin/mausbot-db-copies`** and `sudo chmod 755` it. It writes a consistent copy of each database into a folder beside the data:

   ```sh
   #!/bin/sh
   # Copies of the server's own databases, each consistent, made while it runs.
   # Usage: mausbot-db-copies STATE_FOLDER COPIES_FOLDER
   set -eu
   umask 077
   state=$1 copies=$2
   mkdir -p "$copies/sync"
   for db in messages.db runtime.db bursts.db sync/index.db; do
     [ -f "$state/$db" ] || continue
     rm -f "$copies/$db.tmp"
     sqlite3 "$state/$db" ".timeout 5000" "VACUUM INTO '$copies/$db.tmp'"
     [ "$(sqlite3 "$copies/$db.tmp" 'PRAGMA quick_check;')" = ok ]
     mv "$copies/$db.tmp" "$copies/$db"
   done
   ```

4. **On B, save this as `/usr/local/bin/mausbot-standby-pull`.** It asks A for fresh database copies, then copies every other file, leaving the live databases out:

   ```sh
   #!/bin/sh
   # On the standby: bring its copy of server A up to date. Run every minute.
   set -eu
   A=${A:?how this standby reaches A over SSH, such as root@server-a.example.com}
   DATA=${DATA-/opt/openmausbot/data}         # the data folder here
   STATE=${STATE-.openmausbot}                # the server's own folder inside it
   COPIES=${COPIES-/opt/openmausbot/db-copies}
   A_DATA=${A_DATA-$DATA} A_COPIES=${A_COPIES-$COPIES}   # the same paths on A

   # 1. On A: fresh copies of the databases.
   ssh "$A" "mausbot-db-copies '$A_DATA/$STATE' '$A_COPIES'"
   # 2. Every other file. The live databases, A's process records, sockets
   #    and half-written *.tmp files stay out. Exit 24: a file vanished mid-copy.
   s=/$STATE/; [ "$STATE" = . ] && s=/
   rsync -a --delete --delete-excluded --numeric-ids \
     --exclude "${s}messages.db*" --exclude "${s}runtime.db*" --exclude "${s}bursts.db*" \
     --exclude "${s}sync/index.db*" --exclude "${s}engine-runs/" --exclude '*.sock' --exclude '*.tmp' \
     "$A:$A_DATA/" "$DATA/" || [ $? -eq 24 ]
   # 3. The database copies, kept beside the data until a takeover.
   rsync -a --delete --numeric-ids "$A:$A_COPIES/" "$COPIES/"
   echo "$(date -u +%FT%TZ) copied"
   ```

5. **On B, save this as `/usr/local/bin/mausbot-takeover`.** You run it only when B takes over:

   ```sh
   #!/bin/sh
   # On the standby, once A is stopped and cannot start again: the last copy becomes the data.
   set -eu
   DATA=${DATA-/opt/openmausbot/data}
   STATE=${STATE-.openmausbot}
   COPIES=${COPIES-/opt/openmausbot/db-copies}
   [ -f "$COPIES/messages.db" ] || { echo "no copy of messages.db in $COPIES: nothing to take over" >&2; exit 1; }
   for db in messages.db runtime.db bursts.db sync/index.db; do
     [ -f "$COPIES/$db" ] || continue
     rm -f "$DATA/$STATE/$db-wal" "$DATA/$STATE/$db-shm"
     cp "$COPIES/$db" "$DATA/$STATE/$db"
     chown --reference="$DATA/$STATE" "$DATA/$STATE/$db"
   done
   # The copied lease names A. Removing it says: A is not running on this data.
   rm -f "$DATA/$STATE/openmausbot-server.lease"
   echo "ready: start the server"
   ```

6. **Run the pull every minute on B.** Save `/etc/cron.d/mausbot-standby` on B:

   ```sh
   A=root@server-a.example.com
   * * * * * root flock -n /run/mausbot-standby.lock /usr/local/bin/mausbot-standby-pull >> /var/log/mausbot-standby.log 2>&1
   ```

   For the npm service, add the lines `DATA=/home/maus` and `COPIES=/home/maus-db-copies` above the schedule. `flock -n` skips a minute while the previous copy still runs. Check `/var/log/mausbot-standby.log` after a few minutes: one `copied` line a minute.
7. **Put one address in front.** Your apps, webhooks and connected apps keep working after a takeover only if the address they use moves to B. Give your domain's DNS record a short TTL (60 seconds) so a change reaches people quickly. For the installer, Caddy on B gets its own certificate once the domain points at B.
8. **Watch A.** From B, or from a third place, check A directly every minute:

   ```sh
   curl -sf --max-time 10 --resolve maus.example.com:443:A_PUBLIC_IP https://maus.example.com/api/health | grep -q openmausbot
   ```

   Alert yourself when it fails several times in a row.

## Take over

1. **Make sure A is stopped and stays stopped.** Power it off from your provider's console, or detach its network. Do not rely on A being unreachable from B: a server cut off from B may still be running, answering people who reach it and running its routines. A server that restarts on its own (Docker's `restart: unless-stopped`, a systemd unit with `Restart=always`, a reboot) starts again on A's data without asking.
2. **Stop the copies,** and wait for one that is still running:

   ```sh
   sudo rm /etc/cron.d/mausbot-standby && sudo flock /run/mausbot-standby.lock true
   ```

3. **Put the last copy in place:** `sudo mausbot-takeover`. For the npm service: `sudo DATA=/home/maus COPIES=/home/maus-db-copies mausbot-takeover`.
4. **Start B:** `cd /opt/openmausbot && sudo docker compose up -d`, or `sudo systemctl enable --now openmausbot`.
5. **Move the address** to B: change the DNS record to B's public address.
6. **Check:** `https://maus.example.com/api/health` answers, and the app connects. B has the same server id and the same paired sessions as A, so paired devices should stay signed in.
7. **Look at what was running.** A routine due in the last minutes may run again on B (see the limits below). Sign an engine in again if B says it is not signed in.

## Bring A back

Treat A as the new standby, never as the server it was. A starts MausBot by itself when it boots, so:

1. Boot A with its network detached, or in your provider's rescue mode.
2. Stop MausBot there and keep it from starting: `cd /opt/openmausbot && sudo docker compose stop`, or `sudo systemctl disable --now openmausbot`.
3. Move its old data aside: `sudo mv /opt/openmausbot/data /opt/openmausbot/data.old` (or the npm service's `.openmausbot`).
4. Attach the network again and set up the copies the other way, from B to A.

Anything made on A after the last copy is only in `data.old`; MausBot cannot merge it into B.

## Limits

- **Not automatic.** Deciding that A is gone, stopping it for good, running the takeover and moving the address are yours to do, by hand or with your own tools. Do not take over automatically unless the same tool can also power A off.
- **One active server.** Two servers on copies of the same data are two different servers with the same identity. Their chats diverge and cannot be merged.
- **The last copy is what you get.** Work done on A after it is lost. Copying more often than every minute narrows the gap; it never closes it.
- **Each copy rewrites the databases in full.** With databases of several GB, a copy every minute is too often for A's disk and your network: copy less often and accept a bigger gap. A needs free disk for one copy of the databases.
- **The copies are not taken at one instant.** Each database is consistent on its own, but the databases and the other files are copied seconds apart. After a takeover, something made in those seconds may be missing in one place and present in another.
- **Routines can run twice.** B knows only the routine runs that were in the last copy. A routine run on A since then looks unrun to B, which runs its most recent occurrence late (one that came due within the last 12 hours) and marks older ones as missed.
- **Copied as plain files, not checked:** a bot's Data tables (`bots/<id>/data.duckdb`), the engines' own databases (such as `~/.codex/*.sqlite`), browser sign-ins and bots' work folders. A file being written at the moment of a copy may not open on B.
- **Engine sign-ins** are copied from A. An engine that renewed its sign-in after the last copy may ask you to sign in again on B.
- **Same or newer version.** A server refuses data written by a newer MausBot. Keep B on A's version.
- **Secrets travel with the copy.** The data folder holds saved keys, logins (`logins.json.enc` with its key file `logins-key` beside it), engine sign-ins and paired sessions. Protect B, the copies and the SSH key as you protect A.

## What we tested, and what we did not

We ran the three scripts on this page, as printed, with MausBot 0.1.173 (`openmausbot serve`, the npm package) on one computer: two data folders laid out as the installer lays them out, `ssh` replaced by a local shell, and every command run as one user. A made 60 bots while B pulled 250 times; then A was stopped with `kill -9`. To stand in for a second machine, we edited the copied lease to name another machine: B then refused to start (`This OpenMausBot data directory is already owned by a process on another machine`). After `mausbot-takeover`, B answered in under a second with every bot from the last copy, and the 3 bots made on A after it were missing, as expected. A device paired on A was signed in on B, and both had the same server id. A second server on B's folder was refused. A, started again on its own folder, ran beside B.

Separately, `VACUUM INTO` copied a 400 MB database in about 2 seconds while another process wrote to it as fast as it could. SQLite's `.backup` command, under the same load, did not finish until the writing stopped, because it starts over whenever the database changes.

**Not tested by us; standard practice:** two servers in two places, `ssh` and `rsync` between machines (including rsync's exit code 24), `cron` and `flock`, `chown --reference`, running the scripts as root, the Docker install (`docker compose`) as active or standby, DNS failover, Caddy's certificate on B, the health check, and bringing A back. Also not tested: the desktop and phone apps reconnecting after a takeover, webhooks and connected apps, a tunnel in front (`serve --tunnel`, a Cloudflare tunnel of your own, Tailscale), and phones paired through MausBot Relay. Do not run A and B behind the same tunnel at once: a tunnel with two connectors may send each request to either server. The routine behaviour and the refusal of newer data above are read from MausBot's code and docs, not tested here.
