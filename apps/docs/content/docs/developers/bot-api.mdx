Each bot can take messages from outside: an app or a script sends it a message with a key and gets its reply. It is off by default, per bot. The [client SDKs](/docs/developers/sdks/typescript) wrap everything on this page; use them unless you want raw HTTP.

## Turn it on

In Bot settings (the gear in the bot's panel; **Advanced**, **Access**), find **Bot API** and switch on **Let apps talk to this bot**. The card shows the command to paste, with the key filled in.

The key is shown that once and kept hashed; when the card is opened again the command shows `YOUR_KEY` in its place. **New key** replaces the key, so apps using the old one stop working. Switching the card off forgets it. Only someone who may edit the bot can switch it on, mint a key or switch it off. Each of those is a **Bot API** row in Settings, Activity.

Bot API isn't part of a Cloud's Starter plan. There the card shows one line and **Upgrade**, and a key left from a higher plan answers `403` with an upgrade message. An upgrade works at once, with the same key. Desktop and self-hosted servers aren't affected.

## Call it

```sh
curl -X POST "https://your.domain/hooks/api/v1/bots/<botId>/messages" \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{"message": "Hello! What can you do?"}'
```

The address lives under the webhook receiver's `/hooks` path, so wherever this bot's webhooks are reachable (a Cloud's public name, a self-hosted edge that forwards `/hooks/*`, or `OMB_WEBHOOK_PUBLIC_URL`) the API is too. Nothing new to open. See [Networking](/docs/self-hosting/networking).

Use the `/v1` address for anything you keep. The same calls also answer at `/hooks/api/bots/<botId>/messages`, and that address keeps answering as it always has, but only `/v1` has the promises below.

### What a version promises

Within `/v1` we only add optional request fields and new response fields. A new `status` value, a removed or renamed field, or a changed status code needs `/v2`.

### The request

The JSON body takes:

| Field | |
|---|---|
| `message` | Required, up to 20,000 characters. What to tell the bot. |
| `thread` | Optional. The `thread` an earlier answer returned, to go on in the same conversation. Only a thread the API opened can be continued this way. |
| `wait` | Optional, seconds, at most 300. How long to wait for the reply before answering `working`. The default is 50, under the 60 seconds of silence Fly's proxy is reported to allow. A longer wait is for a path you know keeps a quiet connection open. |

### The answers

| Answer | Meaning |
|---|---|
| `200 {"reply": "…", "thread": "<id>"}` | The bot's reply, text only. |
| `202 {"thread": "<id>", "status": "working"}` | The bot is still at it. Read the thread later with `GET …/messages?thread=<id>` and the same key. |
| `202 {"thread": "<id>", "status": "needs_approval"}` | The bot asked for an approval. Nobody outside can give it: the person opens the thread in the app and answers there. A later `GET` returns the reply. |
| `200 {"thread": "<id>", "status": "failed", "error": "…"}` | The job failed, or someone stopped it in the app. Sent to the call itself or to a later `GET`. |

`error` is one of two fixed sentences, never the engine's own words: "The bot could not answer. Open this thread in the app to see why." or "Someone stopped this in the app." A `failed` thread stays `failed` for the API. To try again, send the message again, or open the thread in the app. The cause stays on the card.

The errors:

| Status | Meaning |
|---|---|
| `400` | Bad body. |
| `401` | Wrong key. |
| `403` | The API is off for this bot (or there is no such bot), or the bot's AI can't run confined. |
| `404` | No such thread. |
| `405` | Not `POST` or `GET`. |
| `409` | That thread is still working, the bot is at its limit of conversations at once, 50 API calls are being answered, or the workspace has moved. A `409` for a thread that is still working carries `{thread, status}` instead of `{error}`. |
| `413` | Body over 256 KB. |
| `415` | Not JSON. |
| `429` | More than ten calls in a minute for this key, or the spend cap. It may carry `Retry-After`, in seconds. |
| `500` | An unexpected error. |
| `502` | The turn never started. |
| `503` | A backup or restore is in progress: try again soon. |

A failure after the turn started is a `200` with `status: "failed"`, as above, not a `502`. The reason stays on the card, not in the response.

## What a call may do

A call starts a normal thread the app shows, marked as sent through the Bot API. Anything in that thread answers only from the bot's standing instructions, its saved memory and the thread itself, whoever writes there next.

- It runs confined and in Ask, whatever the bot's own level, with none of its saved allowances. Nothing answers an approval for the caller.
- It has no shell, computer, browser, phone, connected apps, MCP servers or data tools, and none of MausBot's own tools. It can't start a thread, ask a teammate, make a routine or webhook, change the bot, write its memory or search other conversations.
- It works in the thread's own empty folder, and its words stay out of the person's other conversations. A call that fails shows on the card and in its thread, and reports to no Chief.

A bot whose AI can't run confined answers `403`. Claude, Codex and the API-key AIs can run confined. A key goes when the teammate who made it leaves.

## A key that acts as you

Off by default. For a server you run yourself, with bots doing work for you unattended, the owner can mark a bot's key **Acts as me** on its Bot API card. A thread that key opens then runs as the owner's own work, like a routine they wrote: at the bot's own access level, with its saved allowances, unconfined, with the bot's tools.

<Callout type="warn" title="A marked key is the owner's password">
  Anyone holding a marked key can make the bot do anything its level allows. The bot can also hand work to its teammates, which act at their own access level. Treat the key like the owner's own password.
</Callout>

The never-list, the holds the bot's level puts on sends and other outbound actions, and the computer rules still apply. At Ask, an approval still waits for the owner in the app and the call answers `needs_approval`.

- Only the owner marks a key: on a server one person uses, or on a personal Cloud. Never on a team's Cloud or a shared or hosted workspace, unless its operator set `OMB_SHARED_WORKSPACE_FULL_ACCESS=1`.
- Never for guest links or webhooks. Only a Bot API key carries it.
- **New key** starts without the mark, and switching the API off forgets it.
- A thread keeps what it was opened as. One opened with the mark can't be continued through the API once the key no longer acts as the owner, and answers `403`.

Each call is shown on the card (count, last call, recent calls) to those who can manage the key, and a call taken this way shows "as you". The card never holds the key.
