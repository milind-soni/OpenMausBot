The Local VM gives each bot a containerized Linux desktop on the same machine as MausBot. It is useful for browser work, downloads, and repeatable automation that should not run directly on your host desktop.

## Requirements

- Docker Desktop, Docker Engine, or a supported Podman setup
- Enough local memory and disk for the desktop image
- A healthy container runtime available to the OpenMausBot process

On Windows, Podman is the preferred Local VM runtime. MausBot checks Podman before Docker and validates the exact Windows-to-VM workspace mount before reusing a container.

Before starting two desktops on Windows, confirm the Podman machine is running and has enough shared CPU, memory, and disk for both. Podman Desktop exposes that machine under **Settings → Resources**; both MausBot desktops consume the same machine budget.

## Run two bot desktops

1. Open **App Settings → Bot desktops**, prepare the managed desktop image, and choose **Per bot**.
2. Set **Maximum per-bot desktops** to `2`.
3. Give two bots **Private desktop** as their computer and create each desktop from that bot's Screen panel.
4. Choose **Open two desktops** from either bot to watch both in one workspace.

Both desktops may keep running, but only one pane can hold interactive control at a time. Switching control releases the previous pane first; opening the two-up workspace never creates or starts a VM.

The equivalent source configuration is:

```json
{
  "localVm": {
    "mode": "per-bot",
    "maxInstances": 2
  }
}
```

Local VMs always run on the same physical host as the OpenMausBot desktop process. `maxInstances: 2` does not pool one VM from a Mac and another from a Windows PC. To use Windows capacity today, run MausBot on Windows with its supported Podman lane and create both per-bot desktops there. The BYO-VPS backend is limited to an x86_64 Linux Docker host; do not point it at Windows as a substitute remote Local VM. Cross-host Mac and Windows pooling is tracked in [issue #508](https://github.com/milind-soni/OpenMausBot/issues/508).

## Memory and CPU

Each desktop gets 4 GiB of memory (swap capped at the same) and 2 CPUs. To change that, set `memoryGb` (2 to 128) and `cpus` (1 to 64) in `config.json`:

```json
{
  "localVm": {
    "memoryGb": 8,
    "cpus": 4
  }
}
```

A new desktop is created with these limits. On Docker and Podman, a stopped desktop takes them the next time it starts. On Apple container, remove and recreate the desktop to apply them. Every running desktop counts against the machine's memory, so leave room for MausBot itself.

## Installing packages

A bot can install system packages in its desktop with `sudo apt-get install`. Packages installed this way live in the desktop's own filesystem, not the durable workspace, so recreating the desktop (or an update that recreates it) removes them. User-level installs such as `pip install --user` or anything under `~/.local` are stored in the workspace and survive recreation.

On Linux with Docker Engine, a desktop's root account is the host's root account. Those desktops therefore run with `no-new-privileges`: `sudo` is off and system packages cannot be installed. User-level installs still work. Use rootless Podman on Linux when a bot needs `sudo` in its desktop.

## Linux accounts

On Linux with Docker Engine, the desktop's `cua` account takes the user ID and group ID of the account running MausBot, so files the bot writes in its workspace belong to you on the host. The first start of a new desktop takes longer while it does this. Rootless Podman maps the IDs itself.

## Persistence

The bot's workspace and browser profile live in a durable mounted directory. Recreating the desktop can repair stale runtime state without deleting the durable workspace.

## Ownership and reuse

Local VM ownership uses a renewable lease. MausBot validates the resolved image and container safety contract before reuse instead of trusting only a mutable image tag.
