The Local VM gives each bot a containerized Linux desktop on the same machine as OpenMausBot. It is useful for browser work, downloads, and repeatable automation that should not run directly on your host desktop.

## Requirements

- Docker Desktop, Docker Engine, or a supported Podman setup
- Enough local memory and disk for the desktop image
- A healthy container runtime available to the OpenMausBot process

On Windows, Podman is the preferred Local VM runtime. OpenMausBot checks Podman before Docker and validates the exact Windows-to-VM workspace mount before reusing a container.

Before starting two desktops on Windows, confirm the Podman machine is running and has enough shared CPU, memory, and disk for both. Podman Desktop exposes that machine under **Settings → Resources**; both OpenMausBot desktops consume the same machine budget.

## Run two bot desktops

1. Open **App Settings → Local VM**, prepare the managed desktop image, and choose **Per bot**.
2. Set **Maximum per-bot desktops** to `2`.
3. Give two bots **Local VM** as their computer and create each desktop from that bot's Computer panel.
4. Choose **Open two desktops** from either bot to watch both in one workspace.

Both desktops may keep running, but only one pane can hold interactive control at a time. Switching control releases the previous pane first; opening the two-up workspace never creates or starts a VM.

The equivalent source configuration is:

```json
{
  "localVm": {
    "mode": "per-bot",
    "maxInstances": 2
  }
}
```

Local VMs always run on the same physical host as the OpenMausBot desktop process. `maxInstances: 2` does not pool one VM from a Mac and another from a Windows PC. To use Windows capacity today, run OpenMausBot on Windows with its supported Podman lane and create both per-bot desktops there. The BYO-VPS backend is limited to an x86_64 Linux Docker host; do not point it at Windows as a substitute remote Local VM. Cross-host Mac and Windows pooling is tracked in [issue #508](https://github.com/milind-soni/OpenMausBot/issues/508).

## Persistence

The bot's workspace and browser profile live in a durable mounted directory. Recreating the desktop can repair stale runtime state without deleting the durable workspace.

## Ownership and reuse

Local VM ownership uses a renewable lease. OpenMausBot validates the resolved image and container safety contract before reuse instead of trusting only a mutable image tag.

## Cua Spaces (optional)

If you use [Cua Spaces](https://cua.ai/docs/spaces/quickstart), Local VMs can run as Spaces instead of OpenMausBot's own container. A Space can be a Linux desktop or, on a Mac with Apple silicon, a macOS virtual machine.

1. Install Cua Spaces (`curl -fsSL https://cua.ai/install.sh | sh`) and keep the Cua Spaces app running.
2. Open **App Settings → Computers** and turn on **Use Cua Spaces for Local VMs**. Without a usable install the switch stays disabled and links to the installer.
3. Choose the default OS. Bots can override it in shared or per-bot mode; pool seats always use the default OS.

The Computer panel keeps showing a live preview from screenshots. **Open live desktop** opens the Space in its own window, where you and the bot can both work; **Take control** first pauses the bot, and closing the window or **Hand back** lets it continue. In Cua Spaces each Space is listed as `OpenMausBot: <bot name> (Linux|macOS)`, and the label follows when you rename the bot.

A Space keeps its whole disk until you delete it; there is no mounted host folder. The first macOS Space downloads about 27 GB, and macOS allows two macOS virtual machines at a time. macOS Spaces also need **System Settings → Privacy & Security → Local Network** turned on for the Cua Spaces app, and for OpenMausBot to open a macOS Space's window.

The idle timeout suspends a Linux Space or stops a macOS Space, preserving its files for the next turn. OpenMausBot restores idle timers for its already-running bot Spaces after a restart, even if you switched back to the container backend. Deleting a Space is different: Auto will not silently recreate it; explicitly create it again when you want it back. Deleting a bot also cleans its old per-bot container workspace and both OS Spaces, regardless of which backend is selected.

Ownership is scoped to your OpenMausBot data directory. OpenMausBot records a Space before starting its creation and will not adopt, stop, relabel or delete a Space merely because its name matches. A name collision is shown as unmanaged; delete that Space in Cua or rename it before creating one here.

For macOS Spaces, the viewer web origin is served inside the guest the bot controls. Its viewer window has clipboard, keyboard-lock and pointer-lock permissions, like the container noVNC viewer. Treat the guest and its viewer as bot-controlled content, not a trusted host application.

```json
{
  "localVm": {
    "backend": "cua-spaces",
    "spacesOs": "linux"
  }
}
```

Cua Spaces is separate software under its own license; OpenMausBot does not include it and only calls the `cua` command you installed.
