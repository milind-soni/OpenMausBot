## Bots and threads

A bot is a durable agent identity. A thread is one conversation with that bot and has its own transcript, model, provider session, approvals, costs, and running state. Optional folders organize related threads without duplicating the bot's memory or skills.

Use separate threads when you want fresh context or independent work without duplicating the bot. Messages sent to a busy thread are queued, and supported providers can be steered while they work. Other threads can continue independently. See [Bots, folders, and threads](/docs/features/bots-and-tasks) for limits and shared-resource behavior.

## Groups

Groups bring several bots into one conversation. Each participant keeps its own provider state. Group timeouts prevent a participant from blocking the whole group indefinitely. Existing channels and their thread histories remain intact; the new label does not change turn-taking or delegation.

### Dynamic conversations

Choose **Dynamic** in the group's response menu, or during room setup. This is a
saved room setting, alongside a designated lead, everyone replying, and
mentions only. Members choose the next relevant speaker from the conversation;
a previous speaker can respond again. Each uses its own configured model.

The first participant can answer and select the next speaker in one turn. When
a participant proposes ending, one private scheduling check decides whether an
unanswered contribution remains. These checks use the participant's model and
incur normal provider usage, but their control text is not posted to the chat.
Ordinary replies retain the member's usual tools and permissions.

After 16 public bot replies without a new user message, the room posts a wrap-up
reminder after each reply. Members have room to finish open points; the room
stops at 22 replies. Private checks, posted invitations and system notices do
not count as public replies. A new user message starts a fresh allowance. You
can also press Stop; a queued message is taken up after the current turn ends.

A Chief can set `response_mode: "dynamic"` with `create_room`, and provide an
`opening_message` to post one shared invitation and start the discussion. Without
that field, creating a room does not start paid turns. `manage_room` with action
`set_response_mode` changes an idle room's mode. Existing section boundaries and
approval requirements still apply. A normal `post_to_room` remains a notification
and does not start a discussion.

**Finish together** (Goal mode) remains a separate coordinator-led workflow.

### Meeting limits

Open the timer button beside the response menu to set reply, token, time, or
dollar limits. Each enabled limit has a wrap-up point and a hard stop; combine
them as needed. The first limit reached governs the meeting. The defaults remain
wrap-up after 16 public replies and stop at 22. A custom selection replaces these
defaults, so a time-only meeting does not also have a 22-reply cap.

Every participant request includes the remaining allowance. Wrap-up asks members
to finish open work, rather than stop immediately. Token, time and dollar
reminders can begin earlier when observed turns need more room to finish.
Participants can finish naturally before any limit. Limits apply to Dynamic,
everyone, mentions, designated-lead and Goal conversations without changing who
speaks. A new human message starts a fresh allowance; bot continuations reuse it.

Tokens include all input and output, including cached input and Dynamic's
private scheduling checks. These checks decide who speaks or whether to finish;
they do not count as public replies. Time starts when discussion dispatch begins.
Dollar allowances use a snapshot of OpenRouter's public model rates, including
reported cache discounts, even when the participant uses another connection.
They are estimates, not a provider billing cap. Models without unambiguous,
supported token pricing cannot start a dollar-limited meeting. Fixed request fees
and tiered rates are not supported. Missing complete provider usage stops a
token- or dollar-limited meeting instead of continuing without accounting.
An in-flight request can exceed a token or dollar cap before usage arrives.

A Chief can pass `meeting_limits` to `create_room`, or use `manage_room` with
`action: "set_meeting_limits"` on an idle room. For example,
`{"time":{"seconds":300,"wrapUpSeconds":210},"cost":{"hardStopUsd":0.5,"wrapUpUsd":0.35}}`.
Use `null` to restore the 16/22 default. The dialog preserves its size when limits
are toggled; question-mark buttons explain each field.

## Delegation

Bots can hand work to other bots. Delegated runs carry explicit status back into the parent conversation, including completion, failure, and cancellation.

## Rewind and branches

Editing an earlier message creates a new conversation path. OpenMausBot avoids resuming stale provider sessions after a rewind, so the next turn follows the visible branch rather than hidden abandoned state.

## Memory and working folders

Bot memory is visible and editable. A bot may also have a dedicated working folder; groups can use a shared working folder. Cloud workspaces use a stable default so generated files remain discoverable across threads. A sidebar folder is only organization, not a working directory or a permission boundary.
