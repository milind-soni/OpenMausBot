# Inkbox communication release

> Historical design stage. Later conversation, approval and release decisions are documented in [the current Inkbox release guide](../../verification/inkbox-release.md). The user has now tested iMessage and authorized one PR.

The user authorizes a broader Inkbox release plus fixes for slow responses, raw Markdown in iMessage, visible question codes, and a new task per message. Keep the original implementation on feat/trusted-contacts, uncommitted until the user tests and requests one PR. No reference repo code copying. No live provider writes, external test messages, purchased resources or user-data mutation tests.

Conversation UX: reuse the same owner/bot conversation task across ordinary messages, across restarts, keeping task context. NEW explicitly starts separate work. Preserve exact pending approval targeting. Questions show their actual options and simple reply instructions without request codes. Keep internal correlation; action approvals retain exact once-only codes. Format regular iMessage/SMS responses into readable plain text without Markdown markers, preserving code, URLs and meaningful punctuation. Never alter approval command details. Diagnose latency and remove avoidable polling/global queue wait, expose prompt delivery quickly and ensure deferred results arrive automatically.

Release scope: connect documented Inkbox communication capabilities through one in-app Inkbox setup, retaining existing credentials and compatibility. Include email, iMessage, SMS/MMS, phone call capability, Slack and agent communication where documented APIs support them. Query actual resources/capabilities, distinguish unavailable/needs setup/connected, never invent WhatsApp support or auto-buy phone numbers. Shared contacts, notes and other supported API capabilities should be accessible through scoped host integration rather than credentials exposed in renderer or bot environment. Exact implementation contracts must follow current official Inkbox docs. Native unsupported channels must be honestly labeled.

Identity/trust: signed webhooks prove provider delivery but not arbitrary email/Slack sender authority. Bind explicit owner addresses/accounts, isolate unrelated contacts and provider conversation scopes, reject spoofed/ambiguous senders and group messages unless an explicit safe routing policy exists. Channel-specific replies preserve provider thread identity. Follow-ups never cross recipients. All actions retain host Ask policy and no uncertain replay. Existing saved configurations must migrate without rotating secrets, duplicating identities or replaying sends.

Verify with synthetic provider HTTP/fake-engine and isolated renderer fixtures, security regressions, typecheck/lint/build and signed OMB2 packaging. Record supported versus provider-blocked capabilities; no launch-ready or live-delivery claim without actual evidence.
