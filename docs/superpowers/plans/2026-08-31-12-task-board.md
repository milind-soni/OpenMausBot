# Task Board Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the fleet a durable, resumable work queue — tasks that survive a restart, depend on each other, get claimed by a bot, heartbeat while they run, and get reclaimed when a bot dies mid-task.

**Architecture:** A SQLite table set (`node:sqlite`, the same dependency-free binding `server/message-db.ts` already uses) holding tasks, links, and comments, plus a dispatcher tick that reuses the queued-task executor pattern from `server/routines.ts`. The board is the durable sibling of `server/delegations.ts`: delegation is RPC-shaped and dies with the process, the board is a state machine that outlives it. Agents drive it through five new tools on the existing agents MCP proxy; the user drives it through one full-page surface built like `RoutinesPage.tsx`.

**Tech Stack:** TypeScript strict, Node 24, `node:sqlite`, Vitest, React 19, Tailwind.

**Spec:** none — this plan is its own spec. Its shape is adapted from the Kanban gap analysis in [fathah/hermes-desktop](https://github.com/fathah/hermes-desktop) (`KANBAN_GAP_REPORT.md`, MIT); no code is copied.

## Global Constraints

See [the roadmap](2026-08-31-00-control-plane-roadmap.md#global-constraints). The ones that shape this plan directly:

- **Persisted files are `0600`.** `messages.db` sets its mode explicitly (`server/message-db.ts`); `tasks.db` does the same.
- **Audit what you authorize.** A task that spends a bot's turn is a decision; every dispatch appends through `appendDecision` (`server/decision-log.ts`), fire-and-forget.
- **Imports land disabled.** Tasks arriving in a team package are `todo` and the board is off until the user turns it on.
- **The capability rule.** A task can only be assigned to a bot whose driver can actually run an unattended turn. The UI reads the flag; it does not offer bots it cannot dispatch.
- **The test floor** (`TEST_COUNT_FLOOR = 1070`) — adding tests never touches it.
- The oxlint `anti-slop` plugin bans `unknown` parameters and returns, runtime `typeof` narrowing, and object parameters. Write concrete types.

**Depends on:** nothing hard. The roadmap lists P1 and P2 as prerequisites; they are not. What they add when they land:
- **P1 (budgets)** replaces the fixed `maxRunning` cap in Task 4 with a budget-derived one. Until then the cap is a config number with a default of 2.
- **P2 (bot profile)** adds a supervisor role that may raise the per-bot concurrency. Until then every bot runs at most one board task at a time.

Neither is required to ship a working board, and neither is blocked by shipping one.

## Background: what the fleet has and what it lacks

| Shape | Module | Survives restart? | Resumable? | Human in the loop? |
|---|---|---|---|---|
| `ask_bot` — synchronous peer call | `server/index.ts:265` | no | no | no |
| `delegate_bot` — async handoff, depth-capped at 1 | `server/delegations.ts` | queue yes, permissions no | no | no |
| Routines — scheduled fresh turns with receipts | `server/routines.ts` | yes | re-run only | no |
| A unit of work that can be blocked, commented on, and picked back up | — | — | — | **missing** |

`MAX_COMMS_DEPTH = 1` (`server/delegations.ts:29`) makes A→B→C structurally impossible, and that property is worth keeping. The board does not raise it. A board task is dispatched by the **server**, at depth 0, exactly like a routine — so a bot creating a task is not a recursive delegation, it is filing work for the fleet.

## Statuses

```
todo · ready · running · blocked · review · done · archived
```

- **todo** — filed, has unmet dependencies or has not been promoted.
- **ready** — claimable. A `todo` task with no incomplete parents is promoted to `ready` by the tick.
- **running** — claimed by a bot, heartbeating.
- **blocked** — the bot could not proceed and said why. Only a human or a `task_unblock` moves it out.
- **review** — finished, awaiting a human read. This is the default terminal state for tasks a bot completes, so nothing silently disappears into `done`.
- **done** — accepted.
- **archived** — hidden from the board, kept in the table.

Only these transitions are legal, and Task 2 tests every one of them:

```
todo    → ready | archived
ready   → running | blocked | archived
running → review | blocked | ready   (ready = reclaimed after a dead heartbeat)
blocked → ready | archived
review  → done | ready | archived
done    → archived
archived→ (terminal)
```

```ts
// server/task-board.ts
// A durable work queue for the fleet.
//
// delegate_bot hands one message to one peer and forgets it; a routine
// re-runs a prompt on a clock. Neither can express "this piece of work
// exists, it is not done, someone should pick it up, and it is still
// true after a restart". That is what this table is.
//
// node:sqlite for the same reason message-db.ts uses it: built into
// Node ≥23.4, so the packaged app gains no native dependency.
import { chmodSync, existsSync } from "node:fs";
import { join } from "node:path";
import { DatabaseSync } from "node:sqlite";

import { DATA_DIR } from "./config.ts";
import { newId } from "./contracts.ts";

export type BoardStatus = "todo" | "ready" | "running" | "blocked" | "review" | "done" | "archived";

/** The only legal moves. Everything else throws, including the ones that
 * look harmless — "done → running" would silently re-run accepted work. */
const TRANSITIONS: Record<BoardStatus, BoardStatus[]> = {
  todo: ["ready", "archived"],
  ready: ["running", "blocked", "archived"],
  running: ["review", "blocked", "ready"],
  blocked: ["ready", "archived"],
  review: ["done", "ready", "archived"],
  done: ["archived"],
  archived: [],
};

let db: DatabaseSync | null = null;
let file = "";

export function boardFile(): string {
  return file;
}

export function openBoard(path = join(DATA_DIR, "tasks.db")): void {
  db?.close();
  const fresh = !existsSync(path);
  db = new DatabaseSync(path);
  file = path;
  db.exec("PRAGMA journal_mode = WAL");
  db.exec(`
    CREATE TABLE IF NOT EXISTS tasks (
      id TEXT PRIMARY KEY,
      title TEXT NOT NULL,
      body TEXT NOT NULL DEFAULT '',
      status TEXT NOT NULL,
      assignee_bot_id TEXT,
      created_by_bot_id TEXT,
      priority INTEGER NOT NULL DEFAULT 0,
      thread_id TEXT,
      result TEXT,
      blocked_reason TEXT,
      attempts INTEGER NOT NULL DEFAULT 0,
      created_at INTEGER NOT NULL,
      updated_at INTEGER NOT NULL,
      started_at INTEGER,
      heartbeat_at INTEGER,
      finished_at INTEGER
    );
    CREATE TABLE IF NOT EXISTS task_links (
      parent_id TEXT NOT NULL,
      child_id TEXT NOT NULL,
      PRIMARY KEY (parent_id, child_id)
    );
    CREATE TABLE IF NOT EXISTS task_comments (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      task_id TEXT NOT NULL,
      bot_id TEXT,
      text TEXT NOT NULL,
      at INTEGER NOT NULL
    );
    CREATE INDEX IF NOT EXISTS tasks_status ON tasks (status, priority DESC, created_at DESC);
  `);
  // Task titles and bodies carry whatever the user or a bot typed.
  if (fresh) chmodSync(path, 0o600);
}
```

Then the row mapper, `createTask`, `listTasks`, `getTask`. Keep every SQL string in this file; nothing else in the tree talks to `tasks.db`.

```ts
// append to server/task-board.ts
export interface StatusPatch { result?: string; blockedReason?: string; threadId?: string }

export function setStatus(id: string, next: BoardStatus, patch: StatusPatch = {}): BoardTask {
  const task = getTask(id);
  if (!task) throw new Error(`no such task: ${id}`);
  if (!TRANSITIONS[task.status].includes(next)) {
    throw new Error(`illegal transition ${task.status} → ${next}`);
  }
  const now = Date.now();
  // Every claim is an attempt, including a reclaim after a dead heartbeat.
  // Without this a bot that crashes on one task retries it forever.
  const attempts = next === "running" ? task.attempts + 1 : task.attempts;
  handle().prepare(`
    UPDATE tasks SET
      status = ?, attempts = ?, updated_at = ?,
      started_at   = CASE WHEN ? = 'running' THEN ? ELSE started_at END,
      heartbeat_at = CASE WHEN ? = 'running' THEN ? ELSE heartbeat_at END,
      finished_at  = CASE WHEN ? IN ('review','done') THEN ? ELSE finished_at END,
      thread_id      = COALESCE(?, thread_id),
      result         = COALESCE(?, result),
      blocked_reason = CASE WHEN ? = 'blocked' THEN ? ELSE NULL END
    WHERE id = ?
  `).run(
    next, attempts, now,
    next, now,
    next, now,
    next, now,
    patch.threadId ?? null,
    patch.result ?? null,
    next, patch.blockedReason ?? null,
    id,
  );
  const updated = getTask(id);
  if (!updated) throw new Error(`task vanished during update: ${id}`);
  return updated;
}

/** todo tasks with nothing left to wait for. An ARCHIVED parent counts as
 * satisfied: abandoning a branch must not wedge everything downstream of
 * it, which is the failure mode of treating archive as "still pending". */
export function promotable(): BoardTask[] {
  return handle().prepare(`
    SELECT t.* FROM tasks t
    WHERE t.status = 'todo'
      AND NOT EXISTS (
        SELECT 1 FROM task_links l
        JOIN tasks p ON p.id = l.parent_id
        WHERE l.child_id = t.id AND p.status NOT IN ('done', 'archived')
      )
    ORDER BY t.priority DESC, t.created_at ASC
  `).all().map(rowToTask);
}
```

  ```ts
  export interface DispatcherOptions {
    now?: () => number;
    /** Hand a claimed task to the turn machinery. Resolves when the turn
     * has been STARTED, not when it finishes — the board tracks the rest
     * through heartbeats and the completion callback. */
    dispatch: (task: BoardTask) => Promise<{ threadId: string } | null>;
    /** Concurrency cap across the whole board. P1 replaces this with a
     * budget-derived number; until then it is config with a default of 2. */
    maxRunning?: number;
    /** A running task whose last heartbeat is older than this is assumed
     * dead and returned to ready. */
    staleAfterMs?: number;
    /** Give up on a task that has been claimed this many times. */
    maxAttempts?: number;
    emit?: (payload: { kind: string; task: BoardTask }) => void;
  }
  export interface Dispatcher { tick(): Promise<void>; start(): void; stop(): void }
  export function createDispatcher(options: DispatcherOptions): Dispatcher;
  export const TICK_MS = 30_000;
  export const DEFAULT_STALE_AFTER_MS = 180_000;
  export const DEFAULT_MAX_ATTEMPTS = 3;
  ```

- [ ] **Step 3: Implement the tick**

Order inside one tick matters and is the whole design: **reclaim → give up → promote → claim.** Reclaiming first means a dead task is back in the pool before the cap is measured; giving up before promoting means a cursed task cannot consume a slot every tick.

```ts
// server/task-dispatcher.ts
export const TICK_MS = 30_000;
export const DEFAULT_STALE_AFTER_MS = 180_000;
export const DEFAULT_MAX_ATTEMPTS = 3;

export function createDispatcher(options: DispatcherOptions): Dispatcher {
  const now = options.now ?? Date.now;
  const staleAfterMs = options.staleAfterMs ?? DEFAULT_STALE_AFTER_MS;
  const maxAttempts = options.maxAttempts ?? DEFAULT_MAX_ATTEMPTS;
  const maxRunning = options.maxRunning ?? 2;
  let timer: NodeJS.Timeout | null = null;
  let ticking = false;

  async function tick(): Promise<void> {
    // A slow dispatch must not let a second tick double-claim.
    if (ticking) return;
    ticking = true;
    try {
      for (const dead of staleRunning(now() - staleAfterMs)) {
        setStatus(dead.id, "ready");
        options.emit?.({ kind: "board.reclaimed", task: dead });
      }
      for (const task of listTasks({ status: ["ready"] })) {
        if (task.attempts < maxAttempts) continue;
        setStatus(task.id, "blocked", {
          blockedReason: `gave up after ${task.attempts} attempts — no progress`,
        });
      }
      for (const task of promotable()) setStatus(task.id, "ready");

      let slots = maxRunning - listTasks({ status: ["running"] }).length;
      for (const task of listTasks({ status: ["ready"] })) {
        if (slots <= 0) break;
        if (task.attempts >= maxAttempts) continue;
        const claimed = setStatus(task.id, "running");
        const started = await options.dispatch(claimed);
        if (!started) {
          // the bot is busy elsewhere; put it back without burning a slot
          setStatus(task.id, "ready");
          continue;
        }
        slots -= 1;
        options.emit?.({ kind: "board.claimed", task: setStatus(task.id, "running", started) });
      }
    } finally {
      ticking = false;
    }
  }
  // start/stop wrap tick in setInterval(TICK_MS) with .unref()
}
```

> `setStatus(task.id, "running", started)` after an already-`running` task would be an illegal `running → running` move. Record the thread id with a dedicated `attachThread(id, threadId)` writer instead, added to `task-board.ts` in this step, and adjust the first test's expectation to match. Do not widen `TRANSITIONS` to allow self-transitions.
