# Bot Profile Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the bot a first-class, addressable, versioned object — one read that returns everything the bot is, one write that changes it, an append-only history that can be rolled back, and a single-bot export that clones an employee without cloning its secrets.

**Architecture:** No new source of truth. A new assembler module reads the five stores that already own the pieces (`store.ts` for identity and engine, `workspace.ts` for memory, `skills.ts` for skills, `routines.ts` for schedules, `composio.ts` for connector intent) and returns one `BotProfileDocument`. Writes go back through each owning module, never around it. Every accepted write appends a row to a per-bot NDJSON version log, using the same discipline as `decision-log.ts`.

**Tech Stack:** TypeScript, Node 24, Vitest, React, zod.

**Spec:** none — this plan is its own spec.

## Global Constraints

See [the roadmap](2026-08-31-00-control-plane-roadmap.md#global-constraints). The ones that shape this plan directly:

- **Exports never carry** credentials, transcripts, memory, grants, absolute paths, engine bindings, or a schedule's active state. `server/package-export.ts` already states this as its contract and this plan does not weaken it.
- **Imports land disabled.**
- **Secrets are write-only.** The profile read must not become a way to read back a key that `config.ts` deliberately hides.

**Depends on:** [P1](2026-08-31-01-usage-accounting-and-budgets.md) — the profile carries `budgetUsd`, which P1 introduces.

## Background: what "first-class" is missing today

`server/bot-profile.ts` exists but patches eight cosmetic fields —
`BOT_PROFILE_PATCH_FIELDS` is name, title, description, notifications, avatarUrl,
avatarCrop, voice, speakReplies. Everything else that makes a bot what it is lives
elsewhere and is not addressable as a unit:

| Piece | Owner today | Reachable as "profile"? |
|---|---|---|
| Identity, engine, computer, autonomy, permissions | `BotRecord` (`server/store.ts:277`) | Partially — 8 of ~25 fields |
| Memory | `MEMORY.md` + `memory/` (`server/workspace.ts`) | No |
| Skills | `server/skills.ts` | No |
| Playbooks | `BotRecord.playbooks` | Only via team export |
| Routines | `server/routines.ts`, keyed by `botId` | No |
| Connector intent | `BotRecord.installedPackage.requiredApps` | Only via team export |

And there is no history: no version log, no diff, no rollback. `/api/teams/export`
(`server/index.ts:3424`) exports **every non-hidden bot** — there is no way to export or
clone one.

### Task 1: The profile document shape and assembler

**Files:**
- Create: `server/profile-document.ts`, `server/profile-document.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface BotProfileDocument {
    identity: { name: string; title: string; description: string; avatarUrl?: string; color: MausColor; voice?: string };
    engine: { instanceId: string; model: string; effort?: EffortLevel };
    execution: { computer?: "cloud" | "vm" | "local" | "off"; cloudBackend?: CloudBackend; cwd?: string };
    autonomy: { autoApprove?: boolean; alwaysAllow: string[]; approvePeerComms?: boolean; chiefOfStaff?: boolean };
    budget: { budgetUsd?: number };
    connectors: { composio: boolean; required: Array<{ slug: string; label: string; reason: string; optional?: boolean }> };
    skills: Array<{ name: string; description: string; enabled: boolean; source?: string; sha256?: string }>;
    playbooks: InstalledPlaybook[];
    routines: Array<{ id: string; name: string; prompt: string; enabled: boolean; schedule: RoutineSchedule; runOn: RoutineRunOn }>;
    memory: { bytes: number; topics: Array<{ name: string; bytes: number }> };
  }
  export function readProfile(botId: string, deps: ProfileDeps): BotProfileDocument | null;
  ```
- `ProfileDeps` is an explicit dependency object `{ store, routines }` so the assembler is testable without booting the harness. `workspace.ts` and `skills.ts` are imported directly — they are already pure filesystem modules keyed by `botId`.

- [ ] Write a failing test: a bot with two enabled skills, one disabled skill, one playbook, one routine, and a non-empty `MEMORY.md` assembles into a document where every section is populated and `memory` reports **byte counts and topic names only**.
- [ ] Write a failing test that is the security property: `readProfile` never returns memory **content**, never returns a Composio key, and never returns `resumeCursors` — the provider session ids the companion sidecar already scrubs. Assert by serializing the document and searching for planted sentinel strings.
- [ ] Write a failing test that a missing bot returns `null` and a bot with no skills, routines, or memory returns a document with empty arrays rather than `undefined` — a consumer must never have to null-check a section.
- [ ] Run `pnpm vitest run server/profile-document.test.ts`; expect FAIL, module not found.
- [ ] Implement `readProfile`, delegating to `store.bot()`, `listSkills()` (`server/skills.ts:183`), `listMemoryTopics()` and `readMemoryFile()` (`server/workspace.ts:118,86`) for sizes only, and `routines.listRoutines()` filtered by `botId`.
- [ ] Run; expect PASS.
- [ ] Commit `feat(profile): assemble a complete bot profile document`.

### Task 2: Applying a profile

**Files:**
- Modify: `server/profile-document.ts`, `server/profile-document.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export type ProfileApplyResult =
    | { ok: true; changed: string[] }
    | { ok: false; error: string; field?: string };
  export function applyProfile(botId: string, patch: DeepPartial<BotProfileDocument>, deps: ProfileDeps): ProfileApplyResult;
  ```
  `changed` is a list of dotted paths (`"engine.model"`, `"autonomy.autoApprove"`) — Task 3's version log records it and Task 6's UI renders it.

- [ ] Write a failing test: patching `engine.model` alone changes the model and reports `changed: ["engine.model"]`, leaving every other field untouched.
- [ ] Write a failing test that a patch is **all-or-nothing**: a patch containing a valid `identity.name` and an invalid `budget.budgetUsd` of `-5` applies neither, and reports the offending field. A half-applied profile is the failure mode that makes rollback untrustworthy.
- [ ] Write a failing test that `applyProfile` refuses to write `skills[].enabled` for a skill whose scan produced warnings and which the person has never enabled — enabling a skill is a human act (`server/skills.ts` policy), and the profile API must not become the way around it.
- [ ] Write a failing test that read-only sections (`memory`, and the derived parts of `connectors`) are rejected rather than silently ignored, naming the field.
- [ ] Run; expect FAIL.
- [ ] Implement: validate the whole patch against a zod schema first, collecting the change list; only then delegate each section — `store.patchBot` for `BotRecord` fields, `setSkillEnabled` (`server/skills.ts:261`) for skills, `routines.update(id, patch)` (`server/routines.ts:245`) for routines. Reuse `parseBotProfilePatch` (`server/bot-profile.ts:69`) for the fields it already covers rather than duplicating its rules.
- [ ] Run; expect PASS.
- [ ] Commit `feat(profile): apply a validated profile patch atomically`.

### Task 3: The version log

**Files:**
- Create: `server/profile-versions.ts`, `server/profile-versions.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface ProfileVersionRow {
    v: 1; at: number; botId: string; changed: string[];
    actor: "user" | "agent" | "import" | "rollback";
    before: Partial<BotProfileDocument>; after: Partial<BotProfileDocument>;
    note?: string;
  }
  export function appendProfileVersion(row: Omit<ProfileVersionRow, "v">): void;
  export function readProfileVersions(botId: string, limit: number): ProfileVersionRow[];
  ```

- [ ] Write a failing test: appending three versions and reading with `limit: 2` returns the two most recent, newest first.
- [ ] Write a failing test that `before`/`after` carry **only the changed paths**, not whole documents — a full-document history would grow without bound and would archive a copy of every skill body on every rename.
- [ ] Write a failing test that a row whose `after` contains a key-shaped value is redacted through `redactSecrets` before it reaches disk, and that the file is created `0600`.
- [ ] Write a failing test that a corrupt line in the middle of the file is skipped and the surrounding rows still read — an append-only log must survive a torn write.
- [ ] Write a failing test that an unwritable log does not throw: `appendProfileVersion` is fire-and-forget, matching `decision-log.ts`. A history that can take down the edit it is recording is worse than no history.
- [ ] Run `pnpm vitest run server/profile-versions.test.ts`; expect FAIL.
- [ ] Implement against `DATA_DIR/profile-versions/<botId>.ndjson`, mirroring the rotation and redaction structure of `server/decision-log.ts:81-120`.
- [ ] Run; expect PASS.
- [ ] Commit `feat(profile): append-only profile version log`.

## Self-review

**Coverage.** The roadmap's P2 asks for one addressable object (Tasks 1–2), version
history with diff and rollback (Tasks 3–4, 6), and single-bot export/clone (Task 5).
All covered.

**Type consistency.** `BotProfileDocument` is defined in Task 1 and consumed unchanged
in Tasks 2, 3, 4. `ProfileApplyResult.changed` (Task 2) is the same `string[]` that
`ProfileVersionRow.changed` (Task 3) stores and `describeChange` (Task 6) renders.
`readProfile`/`applyProfile`/`appendProfileVersion`/`readProfileVersions` are the only
four functions crossing module boundaries.

**The one judgement call worth flagging.** Task 5 exports skills by reference and memory
not at all. That is a narrower reading of "the employee retains its experience" than the
community proposal implies — someone importing a shared persona gets its procedures and
a hash-pinned pointer to its skills, but none of what it learned at the previous desk.
The alternative, shipping memory in packages, turns every shared bot into an
exfiltration path for whatever it wrote down. If the tradeoff should go the other way,
it should go there deliberately, as an explicit opt-in with a diff shown before export —
not as a default.
