# Deliver web chat replies over WebSocket

Give a paired browser one read-only WebSocket for chat updates. Keep HTTP for sending messages, approvals, pairing, and history. Keep server-sent events (SSE) for existing clients and as the direct browser's fallback. A transport change does not grant access to a workspace or establish that a particular device or network allows the site.

Plan reviewed against `f76ff4aaf`. These are proposed change IDs, not open PRs. Land **WS-1, then WS-2, then WS-3**. Only WS-1 branches from current `main`. Each later change branches from its predecessor. No data migration, new port, phone release, or Cloudflare configuration change is planned.

## Contract and design review

Use the existing `/api/events` path. A normal GET returns SSE. An authenticated WebSocket upgrade on the same path returns text messages. The request keeps `since`, `screens`, `window`, and `frames`. A WebSocket message has the proposed shape `{ id?: string, frame: ServerFrame }`. `id` is the existing opaque replay cursor, not a message ID. Live events with an SSE `id` carry the same WebSocket `id`. `hello` keeps its snapshot boundary cursor inside `frame`. A `ping` has no `id`. Neither receipt of `hello` nor a heartbeat commits undelivered messages.

| Review finding | Decision |
| --- | --- |
| The current [broadcast path](../../server/index.ts) builds SSE strings before or during per-person filtering. An independent WebSocket broadcaster could deliver private data or replay a different stream. | Select the authorized event once, then encode it for the transport. Preserve exact SSE output. Keep one sequence, replay buffer, subscriber registry, and access policy. Do not parse SSE text on the server to recover JSON, or reserialize identical events per subscriber. |
| A browser WebSocket can carry cookies. The page that opened it matters. | Use the [existing upgrade dispatcher](../../server/routes/upgrades.ts) and normal request gates before answering the handshake. The direct-browser socket requires a valid paired session and the expected browser origin. Do not add loopback privilege, a query-string credential, or a second login. Reject client application messages. Keep ordinary WebSocket control frames. |
| A `101` handshake can succeed while no reply arrives. A failed HTTP chat snapshot can also close an otherwise healthy stream. | Treat the first valid `hello` as evidence the transport works. Track snapshot failure separately. A sign-in refusal still goes through the existing session check. Neither an expired session nor a failed snapshot is a reason to alternate transports indefinitely. |
| A replay gap, server restart, changed membership, or a socket that closes during snapshot loading can make an old cursor unsafe. | Keep the [existing snapshot and cursor owner](../../src/lib/live-events.ts). Apply the same replay eligibility to both transports. Ignore callbacks from a closed connection. Never resend a user's message to recover the feed. |
| Subscribers affect presence, screen delivery, and phone push suppression. Slow clients can retain large images. | Register a socket exactly once. Unregister it on every close path. Enforce [the existing backlog policy](../../server/sse-fanout.ts) on initial replay and live delivery. Drop only disposable screen frames under pressure. Disconnect and resync rather than dropping a durable reply. Keep an application-level `ping` visible to browser JavaScript. |

Rejected approach: run an SSE-to-WebSocket proxy beside OpenMaus. It would add an internal HTTP connection per browser and a second place to manage credentials, disconnects, and slow clients. The server already owns the authorized events and the upgrade dispatcher.

## WS-1. Separate event selection from SSE encoding

- [ ] **Depends on:** `main`. **Files:** [server/index.ts](../../server/index.ts), [replay buffer](../../server/host/sse-replay.ts), [fanout](../../server/sse-fanout.ts), and their focused tests. Extract the shared subscription code into `server/host/` if needed. Do not enable a new endpoint in this change.
- [ ] Before editing, capture a synthetic SSE baseline on the [isolated fake-engine server](../verification/README.md). Record the ordered frame kinds and cursors, time to first reply frame, retained replay size, and buffered bytes for a slow reader. Use the same fixture and payloads for later comparisons. Do not record private messages or cookies.
- [ ] Move transport encoding behind the audience decision. Keep admin, client, team-member, and person-specific views distinct. Keep `screen` and `power` live-only as in the current replay buffer.
- [ ] **Unit gate:** run the fanout and replay tests and the relevant remote-session tests. SSE clients get the same IDs, data, and ordering as the baseline. A restricted session never falls back to an admin frame.
- [ ] **Live gate:** send one fixture message using the [chat-turn recipe](../verification/chat-turns.md). Interrupt SSE mid-reply and reconnect. Compare the visible final transcript with the stored one. Both contain one user message and one complete reply.
- [ ] **Cost gate:** no second full history or replay buffer. Retain the existing character and frame budgets, including the newest-frame exception. Fail on an extra serialization per subscriber for an identical authorized view. Stop here if SSE regresses.

**Branch result:** WS-1 passed on `test/web-chat-websocket-ws1`. `pnpm typecheck` and 73 focused tests passed. Before and after the change, `node scripts/verify-live-reply.ts --engines claude --cases reconnect --skip-room` passed in a disposable browser workspace. The direct replay probe received the same reply after reconnecting from the user-message cursor, without replaying that user message. Its synthetic replay and slow-reader bounds were unchanged. This did not test WebSocket, the public tunnel, or the affected laptop.

## WS-2. Offer the same read-only feed over WebSocket

- [ ] **Depends on:** WS-1. **Files:** the WS-1 subscription module, [server/index.ts](../../server/index.ts), a WebSocket adapter under `server/routes/`, [remote-session tests](../../server/remote-sessions.test.ts), and the shared wire type for the envelope. Use the existing `ws` dependency. No browser default changes.
- [ ] Accept upgrades only after session, origin, scope, workspace, and availability checks. Apply membership changes, expiry, and revocation to already-open sockets. Confirm the dev proxy and packaged listener use the same handler. No separate listener.
- [ ] **Unit gate:** compare an SSE subscriber and a socket subscriber with identical permissions and cursors. Compare both live delivery and replay. Cover a restricted member, a revoked session, changed membership, a slow reader, and an obsolete cursor. An unauthorized connection receives zero workspace frames.
- [ ] **Live gate:** pair a throwaway browser with the isolated fixture. Observe `hello`, a real reply frame, and application heartbeats over a socket. Revoke only the fixture session. The socket closes, receives no subsequent workspace data, and cannot reconnect with that session.
- [ ] **Cost gate:** use the WS-1 workload with a slow socket and a healthy SSE reader. Stop if the slow socket can queue durable events without a bound, if it stalls the healthy reader, or if a socket adds a second upstream HTTP subscription. Apply the existing 4 MiB disconnect policy and account for a single in-flight frame when checking queue size.

Run `node scripts/verify-websocket-feed.ts` with `OMB_CDP_CHROME` set to a Chromium executable. The check pairs a temporary browser, compares live and replayed replies with SSE, and revokes only the fixture session. It does not change the browser's default transport.

## WS-3. Prefer WebSocket in the direct web app, then pilot it

- [ ] **Depends on:** WS-2. **Files:** [browser live-event controller](../../src/lib/live-events.ts), a small browser adapter beside it, [live-event tests](../../src/lib/live-events.test.ts), a browser fixture under `scripts/testing/`, and the verification recipe. Retain [the encrypted phone relay](../../src/lib/relay-server.ts) as the first choice when a relay link exists. Leave desktop, CLI, and native phone consumers on their current paths.
- [ ] Expose a reversible `auto` or `sse` selection for the pilot. `sse` is the initial release setting. In `auto`, a paired direct web page tries the same-origin WebSocket. Use the React store's existing callbacks, not a second store. Never keep SSE and WebSocket subscribed in parallel.
- [ ] Bound a failed first connection. Proposed pilot budget: if no valid `hello` arrives within three seconds while the tab is visible and online, close the socket and try SSE once. Stay on SSE for that page lifetime. For a previously healthy socket, allow one bounded reconnect from the last committed cursor, then use SSE. Preserve current hidden, offline, asleep, and manual retry behavior. A transport switch must not manufacture a successful sign-in or hide a failed snapshot.
- [ ] **Unit gate:** cover a server with no socket support, an upgrade that never completes, a socket with no `hello`, duplicate close and error callbacks, hidden-tab resume, and loss during hydration. A known sign-in refusal leads to pairing. Only the selected transport owns listeners and timers.
- [ ] **Live gate:** drive the real web UI with a fake engine. Send a distinguishable multi-part reply. Cut the socket mid-reply, let the bot finish while disconnected, then restore connectivity. Repeat with WebSocket unavailable and SSE available. Pass only if the visible text and order match the stored transcript, the user message was sent once, and no reload or re-pair was needed. Also check new UI against an SSE-only server and old UI against the new server.
- [ ] **Cost gate:** compare to WS-1 on the same warm fixture. Proposed review thresholds: zero extra snapshot requests on successful replay, one active subscription per tab, fallback started by the three-second budget plus one timer tick, and no more than 100 ms added to median first-frame latency across 20 identical local runs. These are decision thresholds, not measured results or promises about internet latency.
- [ ] **Operator review before merge:** demonstrate disconnect and recovery in the real browser UI. Check the status labels distinguish the selected transport, a refused session, and a failed snapshot in diagnostics. Log categories only, never cookies, query strings, or chat content.
- [ ] **Separate deployment approval:** keep production on SSE until the operator approves a pilot. On an approved device and network, confirm the public `wss://` connection receives the reply, not just a handshake. If the affected laptop is unavailable or the site is disallowed there, record it as unverified. Do not change device controls. If the pilot regresses, select `sse` and reload the pilot tab. Keep the old build available. Do not revoke sessions or restore data to switch transports.

## Go decision

Approve WS-1 to begin. Do not start a later change until the previous checks pass. Do not make WebSocket the production default until the browser demo and public pilot pass. The earlier public SSE test proved that one paired client could receive events. It did not identify the cause of the laptop warning or prove that WebSocket will fix it.
